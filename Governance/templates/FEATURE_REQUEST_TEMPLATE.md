# Feature Request Template

Use this template to propose a user-facing or operational feature. A request
should explain the problem and intended outcome before prescribing a solution,
so maintainers can evaluate its value, scope, and alternatives.

- **Template version:** 1.0.0
- **Status:** Active

## How To Use This Template

Copy the section below into a new feature request. Replace each prompt with
specific information and link supporting issues, research, or examples. Keep
all sections; write "Unknown" or "Not applicable" with a brief reason when
needed. A request records a proposal, not an approval or delivery commitment.

---

## Feature Request

### Metadata

- **Title:** <short, descriptive title>
- **Requestor:** <GitHub handle(s)>
- **Date:** <YYYY-MM-DD>
- **Status:** Proposed | Needs Discussion | Accepted | Declined | Deferred
- **Related issue(s):** <links or None>

### Problem

Describe who encounters the problem, what they are trying to do, and what
currently prevents or complicates it. Include concrete examples, frequency,
impact, and supporting evidence where available. Avoid presenting a solution as
the problem.

### Proposal

Describe the desired outcome and the proposed feature at a high level. Explain
how it addresses the problem and identify affected users, workflows, APIs, or
operational processes. Include mockups or examples where useful, but do not
assume a particular implementation unless it is a requirement.

### Acceptance Criteria

List observable, testable conditions that must be true for the request to be
considered complete. Use numbered criteria; include relevant error cases,
permissions, accessibility, compatibility, and performance expectations.

1. <Given a context, when an action occurs, then the observable result is ...>
2. <Additional measurable criterion>

### Scope

- **In scope:** <behaviors and user groups included>
- **Out of scope:** <related behaviors deliberately excluded>
- **Dependencies:** <teams, systems, or decisions required>

### Alternatives Considered

Describe at least one reasonable alternative, including improving the existing
workflow or making no change. Compare its benefits and costs with the proposal
and explain why the proposal is preferred, or what information is still needed
to decide.

### Risks and Impact

Identify potential user, security, privacy, reliability, accessibility, and
maintenance impacts. Note assumptions and mitigation ideas.

### Validation

Describe how the acceptance criteria will be verified. Identify relevant tests,
user research, instrumentation, rollout monitoring, and success measures. State
which regression checks are applicable and how existing behavior will be
protected.

### Open Questions

List unresolved questions with an owner or the next step needed to answer each.

## Template Maintenance

Review this template when the feature intake process changes materially.
Propose updates through the normal governance process described in
[`../README.md`](../README.md); keep governance changes within the
`Governance/` folder.
